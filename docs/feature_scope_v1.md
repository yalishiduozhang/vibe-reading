# 功能清单 v1

更新时间：2026-03-24
用途：作为 `plan.md` 之前的功能边界文档。先明确这个项目“第一版到底要做什么、不做什么”，再进入详细排期与进展追踪。

## 1. 项目核心定义

这个项目不是普通的“PDF + AI 聊天框”。

它的目标是做一个开源的研究阅读工作台，让用户在读论文时同时完成三件事：

1. 更好地理解论文
2. 更快地连接代码实现
3. 更自然地长出自己的 idea，并沉淀成文档

所以项目的核心价值不是“总结论文”，而是：

- `Read With Context`：贴着原文理解
- `Read With Code`：把论文和实现连起来
- `Read To Create`：把阅读中的灵感变成输出

## 2. 功能分层原则

### 2.1 P0

第一版必须有。没有这些功能，项目就不能成立，或者会退化成普通 AI 阅读器。

### 2.2 P1

非常重要，但不是第一版阻塞项。可以在 P0 跑通后尽快跟进。

### 2.3 P2

有价值，但放到后续版本，避免项目失控。

## 3. P0 主要功能

## 3.1 原文内联段落卡片

### 功能目标

让 AI 辅助发生在原文阅读现场，而不是发生在侧边栏聊天框里。

### 用户价值

- 降低阅读时频繁切出原文的成本
- 让用户边读边理解，而不是先读完再问
- 保留对原文的空间记忆和上下文感知

### 主要输入

- PDF 文档
- 当前页与当前段落位置
- 用户选择的阅读模式

### 主要输出

每个段落旁可展开的轻量卡片，至少支持：

- 段落摘要
- 段落翻译
- 术语解释
- “为什么这一段重要”

### 交互方式

- hover 显示触发点
- click 展开/收起
- 默认折叠
- 不遮挡原文主体
- 支持一键 pin / copy / 导入笔记

### 成功标准

- 用户可以在不离开当前段落上下文的情况下获得辅助解释
- 卡片不会造成大面积遮挡
- AI 输出能明确绑定到具体段落

### 验收标准

- 至少能对普通学术 PDF 的正文段落生成稳定卡片
- 段落卡片与原文位置绑定，不随滚动错位
- 支持摘要、翻译、术语解释三种最小能力

## 3.2 阅读意图模式

### 功能目标

让系统根据用户当前阅读目标来重排关注重点，而不是对所有人都给同一种摘要。

### 用户价值

- 帮助用户快速进入正确阅读路径
- 减少从头到尾硬读整篇论文的负担
- 让同一篇论文在不同任务下有不同阅读策略

### 第一版支持的阅读意图

- 快速理解贡献
- 看懂方法
- 复现实验
- 找局限和缺陷
- 提取写作逻辑

### 系统响应

系统根据意图调整：

- 高亮优先段落
- 章节导航顺序
- 卡片解释重点
- 推荐先看内容

### 交互方式

- 打开论文时先选模式
- 阅读过程中可切换模式
- 切换后即时刷新热区和解释口径

### 成功标准

- 不同意图下的高亮和解释显著不同
- 用户能感受到“系统真的在为当前任务服务”

### 验收标准

- 至少实现 4 种阅读意图
- 每种意图都能影响段落打分和卡片内容
- 支持用户手动覆盖推荐结果

## 3.3 论文-代码联动

### 功能目标

把论文中的方法、模块、实验配置与实际代码建立可浏览、可确认、可回跳的映射。

### 为什么它是 P0

这是项目最稀缺、也最能拉开差异化的一块能力。很多阅读器只帮助“看懂论文”，但真正做研究和复现的人，需要的是“看完论文后能落到实现”。

### 支持的代码源

第一版建议支持两类输入：

- GitHub 仓库地址
- 本地仓库路径

### 用户价值

- 从论文方法名快速找到代码实现
- 从实验配置找到脚本或参数文件
- 降低论文和 repo 来回切换的成本
- 提高复现和学习速度

### 系统行为

- 索引仓库结构、README、配置文件、关键代码文件
- 抽取类名、函数名、模块名、配置项
- 在论文段落中识别方法名、实验设置、模块术语
- 生成候选映射
- 允许用户确认或修正映射
- 保存确认结果，后续复用

### 关键交互

- 在论文段落卡片中显示“可能对应代码”
- 点击跳到代码文件/函数
- 在代码侧边面板显示“相关论文段落”
- 用户可手动绑定或解除绑定

### 第一版策略

不要追求“全自动百分百正确”。

更稳妥的 P0 做法是：

1. 系统生成候选映射
2. 用户确认/修正
3. 系统记忆用户修正结果

### 成功标准

- 用户能从论文段落跳到相关代码位置
- 错误映射可被人工纠正
- 修正后的映射可复用

### 验收标准

- 支持 GitHub URL 与本地路径两种输入方式
- 至少支持 repo 文件级、函数/类级映射候选
- 支持双向跳转：论文 -> 代码，代码 -> 论文
- 支持人工确认映射

## 3.4 段落旁 idea 捕获

### 功能目标

让用户在阅读中突然想到的想法，可以直接挂在对应段落旁边，而不是散落到别的软件或事后遗忘。

### 为什么它是 P0

这是项目从“阅读工具”变成“研究工作台”的关键一跃。我们不是只想帮助用户消费论文，而是帮助用户在阅读现场产生自己的东西。

### 用户价值

- 灵感不丢失
- idea 与原文保持绑定关系
- 后续回看时知道“这个想法是被哪段论文触发的”

### 记录的内容类型

第一版建议支持 idea 类型标签：

- 灵感
- 疑问
- 改进点
- 可复现实验
- 项目方向
- 写作素材

### 交互方式

- 在段落旁点击“记想法”
- 输入短文本或长文本
- 可添加 tag
- 自动保存页码、段落 ID、原文引用片段、时间

### 成功标准

- 用户能在 5 秒内完成一次想法记录
- 之后能准确回到触发该想法的论文位置

### 验收标准

- idea 必须绑定页码和段落
- idea 列表支持按论文、标签、时间筛选
- 支持编辑、删除、置顶、复制

## 3.5 AI 扩展 idea 文档

### 功能目标

把阅读过程中积累的碎片化想法，整理扩展成更成型的研究文档。

### 用户价值

- 把“零散想法”变成“可用产物”
- 降低从阅读笔记到项目提案的转换成本
- 支持课程作业、proposal、组会、实验计划等场景

### AI 可生成的文档类型

第一版建议至少支持：

- 项目 proposal
- 实验计划
- 相关工作对比提纲
- 组会汇报提纲
- 研究假设清单
- 可执行 TODO 列表

### 生成输入

- 用户选中的 idea 集合
- 对应原文引用
- 用户指定文档类型
- 可选补充指令

### 生成输出

- 结构化文档草稿
- 每一节可带引用来源
- 支持继续编辑与二次扩写

### 交互方式

- 从 idea 面板批量勾选
- 选择“生成文档”
- 选择文档模板
- 生成后进入文档编辑视图

### 成功标准

- 用户能把多条零散 idea 合并成一份结构化初稿
- 生成结果保留与原论文的引用关联

### 验收标准

- 至少提供 3 类文档模板
- 生成文档中保留 idea 来源引用
- 文档支持导出 Markdown

## 3.6 证据链解释

### 功能目标

提高 AI 输出的可信度，特别是方法、实验和关键结论解释。

### 用户价值

- 避免 AI 看似会讲，实际脱离原文
- 提升用户对总结、解释、对比结论的信任
- 为后续公式/图表解释打基础

### 系统要求

每条解释尽量附带：

- 页码
- 段落
- 关键句
- “直接来自原文”还是“模型推断”标记

### 第一版重点覆盖场景

- 段落摘要
- 贡献点解释
- 实验结果说明
- 与代码映射时的证据说明

### 成功标准

- 用户能快速追溯 AI 的依据
- 系统不会把推断伪装成事实

### 验收标准

- 每条高价值解释都能回跳原文位置
- 明确区分摘取、归纳、推断三类输出

## 4. P1 重要功能

## 4.1 双语对照阅读

### 功能目标

解决“悬浮翻译看完就忘”的问题，让原文与译文形成稳定对照。

### 主要形式

- 原文/译文按段对齐
- 忠实直译与精简译文切换
- 术语保留原文

### 为什么是 P1 而不是 P0

它很重要，但它更像“加速理解”的增强功能；相比之下，论文-代码联动和 idea 工作流更能定义项目独特性。

## 4.2 图表解释模式

### 功能目标

支持用户框选图表，理解坐标轴、图例、趋势和与正文结论的关系。

### 价值

对论文阅读尤其关键，很多方法论文真正难读的部分就在图表和实验结果图。

## 4.3 公式解释模式

### 功能目标

对公式、符号、推导步骤做更忠实的解释。

### 特别要求

- 不跳关键步骤
- 不编造原文没有的假设
- 明确哪些是模型补充说明

### 为什么暂列 P1

这是高价值功能，但实现难度和风险都很高，适合在 P0 证据链机制跑通后推进。

## 4.4 Markdown / Obsidian / Anki 导出

### 功能目标

把笔记、idea、文档草稿顺滑导出到现有知识工作流。

### 第一版建议导出对象

- Markdown
- Obsidian 友好格式
- Anki 卡片格式

## 4.5 自定义模型与本地模型接入

### 功能目标

让项目保持开放与长期可用。

### 支持范围

- OpenAI-compatible API
- Ollama
- 自定义 base URL / model name

说明：虽然这是系统层能力，也很重要，但作为用户可见主功能，它可以在实现层与 P0 一起做，在文档优先级上列为 P1 补充能力。

## 5. P2 后续功能

## 5.1 Zotero bridge

### 功能目标

与 Zotero 条目、笔记、元数据做桥接。

### 为什么先不进 P0

它很重要，但涉及额外生态集成与许可边界，放在 P0 容易拖慢主功能成型。

## 5.2 跨论文关联推荐

### 功能目标

在阅读当前论文时，提示与历史论文、方法、数据集的关联。

## 5.3 协作式阅读

### 功能目标

支持多人共读、共享批注、共享 idea。

## 5.4 组会讲稿模式

### 功能目标

将阅读结果自动整理为讲稿、讲解顺序和展示材料。

## 5.5 每日论文推送与候选阅读清单

### 功能目标

从“阅读器”进一步延伸到“研究信息流”。

## 6. 当前版本的功能边界

### 第一版明确要做

- 原文内联段落卡片
- 阅读意图模式
- 论文-代码联动
- 段落旁 idea 捕获
- AI 扩展 idea 文档
- 证据链解释

### 第一版尽量做

- 双语对照阅读
- 图表解释模式
- Markdown 导出

### 第一版先不承诺

- 复杂公式推导解释做到非常强
- 深度 Zotero 双向同步
- 多人协作
- 跨论文知识图谱

## 7. 对后续 `plan.md` 的直接要求

后面的 `plan.md` 需要基于这份功能清单，至少回答以下问题：

1. 每个 P0 功能的实现顺序是什么
2. 哪些功能可以并行开发
3. 哪些依赖开源参考组件
4. 哪些需要先做 PoC 再决定是否推进
5. 每个阶段的可演示成果是什么
6. 进展如何记录与更新

## 8. 当前建议的项目主宣传语

可以先暂定为：

> 一个开源的论文阅读工作台：边读论文，边连代码，边长出自己的 idea。

或者更短一点：

> Read papers, map code, grow ideas.

这两句都比单纯说“AI 论文阅读器”更准确。
