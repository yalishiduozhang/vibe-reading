# 开源版 Vibe Reading 项目方案

暂定项目名：`OpenVibeRead`

项目目标不是做“又一个论文总结器”，而是做一个真正帮助用户保留理解过程、降低认知摩擦、并能进入现有科研工作流的开源阅读环境。

## 1. 一句话定位

一个开源、可验证、可自定义、可本地部署的“原文优先”论文阅读工作台：让 AI 在 PDF 内部帮助用户分配注意力、理解公式图表和联动代码，而不是用一堆侧边栏回答取代阅读本身。

## 2. 为什么这个项目值得做

这个项目有意义，不是因为“AI 看论文”本身新，而是因为它直击了三个真实矛盾：

1. 用户需要更快理解论文，但又不希望被 AI 剥夺思考过程。
2. 传统“PDF + 聊天框”虽然方便，却不断打断阅读流和空间记忆。
3. 很多现有工具只解决“看懂一点”，没有解决“如何记住、复用、进入工作流”。

如果把项目只做成“浮在 PDF 旁边的总结器”，它不会有长期价值。  
真正有潜力的方向，是把 AI 从“问答器”变成“阅读内的认知支架”。

## 3. 目标用户

### 3.1 核心用户

- 阅读英文论文吃力但又需要保留原文理解过程的本科生、硕士生、博士生
- 需要高频看论文和代码实现的算法工程师、科研实习生
- 需要带组讲文献、做组会、写 related work 的研究者

### 3.2 次级用户

- 非英语母语读者
- 注意力容易分散、难以线性长时间阅读的人
- 需要把阅读内容转成笔记、闪卡、写作素材的人

## 4. 我们要解决的核心问题

### 4.1 当前方案的典型问题

1. 聊天框把“提问”做强了，把“阅读”做弱了。
2. 用户常常不知道一篇论文该先看哪里。
3. AI 对公式、证明、图表和实验设置常常解释得不忠于原文。
4. 看完之后难以沉淀为可复用的知识。
5. 结果无法顺滑进入 Zotero / Obsidian / Anki / Markdown。

### 4.2 我们的产品假设

如果把 AI 的帮助做成“贴着原文发生、可追溯、可控制密度、可导出到工作流”的阅读支架，而不是独立聊天框，那么用户会：

- 更快定位关键段落
- 更少跳出原文
- 更容易形成结构化理解
- 更愿意持续使用

## 5. 产品原则

### 5.1 原文优先

AI 的职责是引导，不是抢戏。任何摘要、翻译、解释都不能遮蔽原文的主体地位。

### 5.2 非线性但不失控

帮助用户跳到重要部分，但不能把页面变成充满气泡的噪音墙。

### 5.3 解释必须可验证

尤其是公式、证明、图表和实验结论，AI 输出必须能追溯到原文证据。

### 5.4 开放而不是绑死

支持用户自己的模型、自己的 API、自己的工作流，而不是把阅读结果关在应用里。

### 5.5 插件桥接优先

不强迫用户放弃 Zotero 等既有工具。新系统应尽量作为“增强层”存在。

### 5.6 Local-first

敏感文档、本地模型、离线能力是科研场景的真实需求，不是可有可无的附加功能。

## 6. 相比 Vibero，我们要明确超越的点

### 6.1 开放性

- 开源仓库公开
- 允许用户接入自己的模型/API
- 提供社区版，不把基础体验锁死在付费墙后

### 6.2 许可边界清晰

- 不在 v1 里做“基于 Zotero 改壳再闭源”的路径
- 优先采用“独立阅读核心 + Zotero 插件桥接”的架构
- 若后续深度接入 Zotero 生态，必须单独做许可核查

说明：这不是法律意见，而是工程策略。目标是从一开始规避评论区最强烈的协议质疑点。

### 6.3 忠于原文

- 公式解释必须逐步对齐
- 图表解释必须指出图中区域、坐标和图例
- 任何“推断”都要标记为推断，不伪装成原文事实

### 6.4 工作流闭环

- 一键导出到 Markdown / Obsidian / Anki
- 保留原文引用锚点、页码、段落 ID
- 支持和 Zotero 文献条目联动

### 6.5 跨平台和轻部署

- Web 优先
- Linux 优先支持
- 桌面壳用 Tauri，而不是重型 Electron 优先

## 7. MVP 功能定义

下面是建议的 MVP 范围。它已经能体现“vibe reading”的核心价值，但不会一上来过度铺张。

### 7.1 PDF 内联段落卡片

在每个段落边缘提供轻量触发点，点击后展开：

- 段落摘要
- 逐段翻译
- 关键术语解释
- “为什么这一段重要”

要求：

- 默认折叠
- 不遮挡主体文本
- 支持密度控制

### 7.2 阅读意图模式

用户在开始阅读前选择目标：

- 快速了解贡献
- 复现实验
- 看懂方法
- 扫描缺陷与局限
- 提取写作框架

系统根据意图调整：

- 高亮段落
- 导航顺序
- 解释角度
- 卡片内容

这是最值得超越原版的点之一，因为它把“主动分配注意力”真正做成可控系统，而不是固定 Prompt。

### 7.3 证据链式解释

所有 AI 解释都要附带证据入口：

- 引用来源段落
- 所在页码
- 对齐句子
- 若是推断，则显示“模型推断”

特别适用于：

- 公式理解
- 实验结论核对
- 引理/证明过程追踪

### 7.4 双语对照阅读

评论区明确指出“划过去就忘”的问题，因此建议做：

- 原文与译文并排
- 按段对齐
- 支持只看术语提示
- 支持切换成“精简译文”与“忠实直译”

### 7.5 图表/公式/代码三联动

MVP 先做轻量版本：

- 公式：提取公式区域并提供逐步解释卡
- 图表：框选图后给出图意说明
- 代码：输入仓库地址后，尝试把论文中的模块名、方法名映射到代码文件或函数

### 7.6 拖拽到笔记与闪卡

用户可以把：

- 原文高亮
- AI 摘要
- 图表解释
- 公式卡片

拖入笔记面板，自动生成：

- Markdown 笔记块
- Anki 卡片
- Obsidian 可引用片段

### 7.7 本地模型 / 自定义 API

至少支持：

- OpenAI 兼容接口
- Ollama
- 用户输入自定义 Base URL / API Key / 模型名

## 8. 非 MVP 但值得保留在路线图中的功能

1. 协作式阅读
2. 组会讲稿模式
3. 跨论文关联推荐
4. 与 Zotero 标签和收藏状态双向同步
5. 日报式论文推送
6. 手写笔触发 AI 解释

这些功能都很有潜力，但不应该压到第一版里。

## 9. 交互设计建议

### 9.1 页面结构

推荐采用三层结构：

1. 主体层：PDF 原文
2. 氛围层：贴边卡片、轻量热区、公式/图表锚点
3. 工作台层：笔记面板、代码面板、导出面板

### 9.2 几个关键交互原则

- 默认安静：卡片和提示默认弱存在
- 按需展开：只有在 hover / click / shortcut 下显性化
- 密度可调：轻提示 / 标准 / 深度三档
- 一键回到原文：任何解释都要能迅速收起

### 9.3 最重要的 HCI 指标

- 用户看原文的比例是否增加
- 用户在不同面板之间的切换次数是否下降
- 用户是否更容易回忆论文结构
- 用户是否能更快找到“对自己当前目标最有用”的部分

## 10. 技术架构建议

### 10.1 前端

- `React` + `PDF.js`
- 可选桌面壳：`Tauri`
- 文本层与覆盖层分离
- 用统一坐标映射服务管理：
  - 缩放
  - 翻页
  - 多栏布局
  - 旋转

### 10.2 文档解析层

建议分层做，不要一开始把解析押在单一模型上：

1. 基础层：
   - `PDF.js` 文本层
   - 段落切分规则
2. 增强层：
   - 标题/章节检测
   - 图表/公式区域检测
3. 可选后端：
   - `GROBID` 或类似服务做论文结构提取

### 10.3 AI 任务层

至少拆成四类任务：

1. `Attention Agent`
   - 根据阅读意图打分段落重要性
2. `Inline Explainer`
   - 段落摘要、翻译、术语解释
3. `Faithful Reasoner`
   - 公式/证明/实验解释，必须带证据链
4. `Repo Mapper`
   - 代码仓库索引与论文术语映射

### 10.4 数据层

- 本地元数据：`SQLite`
- 向量检索：本地轻量方案即可
- 缓存：
  - 段落级结果缓存
  - 页面级热区缓存
  - 图表/公式解释缓存

### 10.5 集成层

建议拆成独立 adapter：

- `zotero-adapter`
- `obsidian-exporter`
- `anki-exporter`
- `github-repo-indexer`

这样主应用保持干净，生态扩展不互相污染。

## 11. 开源与许可策略

建议从第一天就把许可策略设计清楚：

### 11.1 仓库拆分

- `core-reader`
- `desktop-shell`
- `zotero-bridge`
- `obsidian-export`

### 11.2 基本原则

- 不复制或魔改 Zotero 主体源码进入 v1
- 如需和现有 AGPL 生态深耦合，单独审查再决定分发策略
- 文档里明确说明哪些模块是独立实现，哪些模块只是桥接集成

## 12. HCI 课程项目的研究价值

这个题目非常适合作为人机交互项目，不只是因为它“用了 AI”，而是因为它天然带有可验证的交互研究问题。

### 12.1 可以研究的问题

1. 内联式 AI 辅助是否比侧边栏聊天式更少打断阅读？
2. 阅读意图模式是否能帮助不同任务的用户更快找到重点？
3. 证据链式解释是否能提升用户对 AI 的信任？
4. 双语对照是否比悬浮翻译更利于记忆保持？

### 12.2 可以做的实验设计

做三组对比：

- A 组：普通 PDF 阅读器
- B 组：PDF + 侧边栏聊天 AI
- C 组：OpenVibeRead

收集指标：

- 找到核心贡献所需时间
- 完成理解题正确率
- 24 小时后的回忆分数
- 任务过程中的切换次数
- NASA-TLX
- SUS

如果你们课程允许，这会是非常完整的一套 HCI 研究路径。

## 13. 分阶段路线图

### Phase 1：做出最小可用的“氛围阅读”体验

目标：证明“原文优先 + 内联辅助”真的有效。

包含：

- PDF 渲染
- 段落切分
- 段落摘要/翻译卡片
- 阅读意图模式
- 热区导航
- Markdown 导出
- 自定义 API / Ollama 接入

### Phase 2：做可信度和工作流

目标：证明这不是玩具，而是能进入真实科研流程。

包含：

- 双语对照
- 证据链式解释
- 公式卡片
- Zotero / Obsidian / Anki 集成
- Linux 桌面支持

### Phase 3：做真正超越 Vibero 的部分

目标：从“好看的内联总结器”升级为“研究工作台”。

包含：

- 图表理解
- 论文与代码映射
- 组会讲稿模式
- 跨论文关联
- 协作式阅读

## 14. 建议的首版仓库任务清单

可以直接拆成这些 issue：

1. `PDF 文本层 + 段落 bbox 提取`
2. `段落卡片 overlay 系统`
3. `阅读意图模式与段落打分`
4. `摘要/翻译 API 适配层`
5. `Markdown/Anki 导出`
6. `Ollama / OpenAI-compatible provider`
7. `双语对照视图`
8. `公式区域框选与解释卡`
9. `Zotero bridge PoC`
10. `HCI 用户实验脚本与问卷`

## 15. 最后的产品判断

如果只是复刻 Vibero 的表面能力，这个项目很快会变成“PDF 上挂几个 AI 气泡”的普通作业。  
如果我们坚持下面这条主线，它就会变成一个真正有研究价值、也有开源价值的项目：

> 不让 AI 替用户阅读，而是让 AI 帮用户更好地阅读、理解、记住，并进入自己的知识工作流。

这才是这个项目最值得做的地方。
